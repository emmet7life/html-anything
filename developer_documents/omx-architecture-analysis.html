1. 总览

html-anything 是一个以 Next.js 16 + React 19 为主应用的 pnpm monorepo。 核心产品形态是「输入任意内容 → 选择模板与 Agent → 流式生成单文件 HTML → 预览、导出、部署、保存历史」。

Product

内容到 HTML

支持 Markdown、CSV、PPTX、图片等输入，经模板 prompt 与 AI Agent 生成可预览的单文件 HTML。

Runtime

本地 Agent 编排

后端 API 不直接调用云模型 SDK，而是 spawn 本地 CLI，例如 Claude Code、Codex、Gemini、OpenClaw。

Persistence

浏览器侧持久化

Zustand + localStorage 保存当前任务，IndexedDB 保存历史版本，生成 HTML 不通过临时文件落盘。

2. Workspace 边界

顶层目录是公共 harness 边界，只保留 workspace 元数据、CI、结构守卫和文档。 业务源码集中在 next/，浏览器级测试集中在 e2e/。

路径 职责 约束
/ pnpm workspace、CI、结构守卫、开发文档 根 package.json 不代理子包脚本，不承载应用源码。
next/ 完整 Next 应用，包括 App Router、组件、lib、public、单元测试 业务逻辑、API 路由、Vitest 测试都在此边界内。
e2e/ Playwright 端到端测试 浏览器测试不能放到 next/，用例集中在 e2e/ui/。 
pnpm-workspace.yaml
  packages:
    - next
    - e2e

常用命令:
  pnpm exec tsx scripts/guard.ts
  pnpm -F @html-anything/next typecheck
  pnpm -F @html-anything/next test
  pnpm -F @html-anything/e2e test

3. Next 应用结构

next/src/app/page.tsx 是单页工作台 shell。它组合工具栏、任务侧栏、历史面板、编辑区、 预览区、欢迎/设置弹窗和浮动生成按钮，并在客户端挂载后检测本机可用 Agent。

界面层

  • Toolbar：Agent 选择、导出、部署、设置入口。
  • EditorPane：输入内容与格式编辑。
  • PreviewPane：iframe 实时渲染生成 HTML。
  • ConvertChip：生成/取消入口，与快捷键共享同一逻辑。
  • TasksSidebar、HistoryPane：多任务和版本历史。

服务层

  • app/api/convert：模板加载、prompt 组装、SSE 转发。
  • app/api/agents：本地 Agent 检测。
  • app/api/deploy：部署配置与发布流程。
  • app/api/templates、marketplace：模板和技能市场。

4. 生成 HTML 链路

生成链路是本项目最核心的数据流：前端触发任务、客户端预处理输入、服务端组装 prompt、 本地 Agent CLI 流式输出，最后由前端将 SSE 事件写回 store 并刷新预览。

1
ConvertChip 触发

点击按钮或使用快捷键，调用 useConvert().run(taskId, agent, templateId, content, format, model)。

2
use-convert.ts 客户端编排

初始化运行状态，内联 asset:<id> 资源，调用 summarizeForAgent() 识别格式，并判断是否进入 diff-edit 模式。

3
POST /api/convert

服务端通过 loadSkill() 加载模板，使用 assemblePrompt() 或 buildEditPrompt() 生成最终 prompt。

4
invokeAgent() spawn 本地 CLI

解析二进制路径、构建 argv、写入 stdin 或命令行参数，并将 stdout/stderr 转换成结构化事件。

5
SSE 回传并实时渲染

前端处理 start、delta、html、meta、done、error 事件，持续更新任务 HTML 与日志。

关键设计： diff-edit 模式把前一版 baseHtml 和 baseContent 一起发送给服务端，要求 Agent 只做最小内容差异修改， 避免每次重新生成导致视觉系统漂移，同时降低输出 token 成本。

5. Agent 适配层

Agent 层由 next/src/lib/agents/ 承担，拆成检测、argv 构建、子进程调用和输出解析。 这让 UI 可以统一面对不同 CLI，同时把每个 Agent 的协议差异封装在边界内。

模块 职责 架构意义
detect.ts 声明 Agent 列表、协议、fallback model、PATH 搜索规则 前端设置页和后端调用共享同一 Agent 事实来源。
argv.ts 按协议构建命令行参数、环境变量和输出 parser 把 stdin、argv、argv-message、检测型协议差异集中处理。
invoke.ts 解析最终 binary，spawn 子进程，输出 ReadableStream<InvokeEvent> 服务端 API 不依赖具体 Agent SDK，降低外部 SDK 耦合。

当前支持的协议包括 stdin、argv、argv-message，并对 acp、 pi-rpc 做检测型展示。对用户显式设置的 binary override，代码选择「错误即报错」而不是悄悄回退， 这是合理的可观测性设计。

6. 状态与存储

应用状态由 next/src/lib/store.ts 管理，使用 Zustand + persist 保存多任务、活跃任务、Agent 设置、 模型选择、布局、语言和欢迎状态。生成历史由 IndexedDB 模块负责，和当前任务状态分层保存。

数据 位置 说明
当前任务与 HTML Zustand + localStorage Task.html 随 SSE 事件更新，支持多任务并发流式写入。
版本历史 IndexedDB history/db.ts 保存每个任务的历史版本，并做保留数量控制。
部署记录 任务内 ring buffer 保存 provider、URL、HTML hash、状态和部署时间，便于识别线上版本。
上传资源 任务 assets map 编辑区只保留 asset:<id> 占位符，提交给 Agent 前恢复为 data URL。

7. 扩展模块

模板系统

templates/ 和 skills/ 提供内置模板、技能注册、安装和预览 API。共享设计指令集中在 templates/shared.ts。

导出系统

export/ 覆盖下载、剪贴板、图片、Markdown 往返、deck、微信、知乎、Bilibili、Mastodon、Bluesky、Notion 等目标。

部署系统

deploy/ 封装 Vercel 配置、发布与 URL 可达性检测，UI 侧由 DeployControl 触发。

8. 测试与守卫

仓库采用结构守卫 + 应用单元测试 + 独立 e2e 测试的三层验证。 scripts/guard.ts 是边界约束的自动化表达，CI 也按同样顺序执行 workspace guard、typecheck、unit test、build 和 Playwright。

层级 命令 验证内容
结构守卫 pnpm exec tsx scripts/guard.ts 目录归属、脚本边界、CI 关键命令和测试位置约束。
Next 类型检查 pnpm -F @html-anything/next typecheck 应用源码 TypeScript 类型正确性。
Next 单元测试 pnpm -F @html-anything/next test HTML 提取、历史 DB、技能、模板、deck viewer 等模块。
E2E pnpm -F @html-anything/e2e test 浏览器级用户流程，例如导出菜单与部署控件。

9. 风险与建议

主要风险

  • Agent CLI 协议持续变化，parser 和 argv 适配需要高回归覆盖。
  • 生成 HTML 全量放入 localStorage 可能遇到容量上限，长文档和多任务会放大风险。
  • SSE 流式解析与任务切换并发相关，容易出现取消、后台任务、预览刷新之间的边界问题。
  • 模板 prompt 体量和共享指令复杂度高，变更会影响所有生成质量。

改进建议

  • 为 Agent parser 增加每个 CLI 的 fixture 回归测试，覆盖 stdout、stderr、tool-use 恢复 HTML。
  • 把大 HTML 的持久化从 localStorage 迁到 IndexedDB，仅在 store 中保留活跃摘要和当前版本 id。
  • 为 convert SSE 协议补一份稳定事件契约文档，约束前后端字段演进。
  • 建立 omx_wiki/ 持久项目知识库，沉淀架构、生成链路、状态存储、Agent 集成和测试约束。
本次 OMX 工具链问题： 原始 omx explore 报错不是项目架构问题，而是 macOS developer directory 指向不兼容的 /Applications/Xcode.app/Contents/Developer。用 DEVELOPER_DIR=/Library/Developer/CommandLineTools 后，xcrun、clang、 cc 均恢复可用，omx explore 也能继续执行。
